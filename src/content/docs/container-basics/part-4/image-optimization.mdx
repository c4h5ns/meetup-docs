## 本番環境用のイメージとマルチステージビルド
### 開発環境用と本番環境用の要件の違い
開発時と本番運用時では、コンテナに求められる役割が大きく異なる。

単一ステージの `Dockerfile` でビルドを行うと、ソースコードのコンパイルに必要なビルドツールや中間ファイル、開発用の依存パッケージがすべて最終的なイメージに含まれる。
イメージサイズの肥大化に加え、アタックサーフェスが増えることによるセキュリティ上のリスクも問題となる。

### マルチステージビルドの仕組み
**マルチステージビルド（Multi-stage builds）** とは、1つの `Dockerfile` 内に複数の `FROM` 句を定義し、ビルド作業を行うステージと、実際にアプリケーションを実行するステージを分離する技術である。

- 前段のステージでソースコードのビルドやパッケージのインストールを行う。
- 後段のステージでは、軽量なベースイメージを採用し、前段からビルド済みの実行バイナリや成果物のみを `COPY --from=<ステージ名>` でコピーする。
- 最終的に生成されるイメージは **最後のステージの内容のみ** となり、前段のビルドツールやキャッシュ、ソースコードは破棄される。

```dockerfile
# ステージ1: ビルド環境 (JDKやMavenツールチェーンを含む)
FROM maven:3.9-eclipse-temurin-21-alpine AS builder
# ...
RUN mvn clean package -DskipTests

# ステージ2: 本番実行環境 (最小限のJREランタイムのみ)
FROM eclipse-temurin:21-jre-alpine
COPY --from=builder /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### 具体的な記述例
#### 例1: Java (Spring Boot)

```dockerfile title="Dockerfile"
# --- ビルドステージ ---
FROM maven:3.9-eclipse-temurin-21-alpine AS builder

WORKDIR /app

COPY pom.xml .
RUN mvn dependency:go-offline -B

COPY src ./src
RUN mvn clean package -DskipTests


# --- 実行ステージ ---
FROM eclipse-temurin:21-jre-alpine

WORKDIR /app

RUN addgroup -S appgroup && adduser -S appuser -G appgroup

COPY --from=builder /app/target/*.jar app.jar

USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

## マルチステージビルドのメリット
### 1. イメージサイズの削減
マルチステージビルドを行うことで、不要なビルドツールや中間ファイルを最終イメージに含めずに済むため、イメージサイズを大幅に削減できる。

1. **コンパイラ・ビルドツールの削減**:  
  コンパイラや標準ライブラリのソース、各種ビルド補助ツール（GCCやGitなど）
2. **中間ファイル・パッケージキャッシュの削減**:  
  パッケージマネージャ（`npm`, `pip`, `go mod` 等）がダウンロードした圧縮アーカイブやキャッシュファイル、中間オブジェクトファイル（`.o` など）
3. **OS自体のフットプリントの最小化**:  
  実行ステージでは必要最小限のパッケージのみを含む軽量ディストリビューション（Alpine Linux や Distroless、あるいは完全な空イメージである `scratch`）を選択

### 2. セキュリティの向上（アタックサーフェスの縮小）
コンテナイメージに含まれるパッケージやツールの数が多ければ多いほど、既知の脆弱性（CVE）が含まれる可能性が高くなる。
また、実行用コンテナ内に `bash` や `curl`, `wget`, `netcat`, パッケージマネージャを含めないことで、攻撃者が不正侵入したとしても、
外部から悪意あるスクリプトをダウンロードして実行するなどの横展開（ラテラルムーブメント）が難しくなる。

### 3. デプロイおよびスケールアウトの高速化
コンテナをクラウド環境（AWS ECS等）で運用する場合も多数メリットが存在する。

- **Push/Pull時間の短縮**:  
  イメージビルド環境からコンテナレジストリへのPushと、コンテナレジストリからコンテナホストへのPull時間を短縮できる。
- **転送コスト、保存コストの削減**:  
  レジストリからのデータ転送費用や、レジストリ上の保存容量を削減できる。
- **オートスケーリングの迅速化**:  
  トラフィック急増時に新しいタスクをスケールアウトさせる際、イメージダウンロードが数秒で完了するため、アクセス急増への追従性が向上する。

### 4. 機密情報・ソースコードの保護
- **ビルドシークレットの漏洩防止**:  
  プライベートリポジトリのアクセストークンや、ビルド時にのみ必要なAPIキーなどをビルドステージで使用しても、実行ステージに引き継がれないため、
  最終イメージを解析されて秘密情報が抜き取られるリスクを防ぐことができる。
- **ソースコードの非公開**:  
  コンパイル言語の場合、ソースコードそのものを除外してコンパイル済みのバイナリのみを配布できる。


## さらなる最適化テクニック
### `.dockerignore` ファイル
プロジェクトルートに `.dockerignore` を配置することで、ビルドコンテキストから特定のファイルやディレクトリを除外できる。

```text title=".dockerignore"
# バージョン管理・環境設定
.git
.gitignore
.env
.env.*

# 依存ライブラリ・キャッシュ
node_modules
npm-debug.log
__pycache__
*.pyc
.cache

# ビルド成果物・ローカルテスト
dist
build
coverage
*.log

# ドキュメント・IDE設定
README.md
.vscode
.idea
```

### レイヤーキャッシュを意識した記述順序
Dockerのイメージレイヤーは、変更があった命令以降のキャッシュが無効化される。
そのため、**「変更頻度が低い命令を上部に、変更頻度が高い命令を下部に配置する」** のが鉄則である。

```dockerfile title="NG"
# 変更頻度が高いソースコードを含むファイルのコピーを上部に配置
COPY . .
RUN npm install
```

```dockerfile title="OK"
# OK: 変更頻度が低い依存関係のインストールを上部に配置
COPY package.json package-lock.json ./
RUN npm install
COPY . .
```
